10/3專題題目與 UML 工具⌄
老師題目我們的答案
專題題目AI 旅遊搜尋平台：以 AI 對話媒合旅行社的套裝行程、機加酒與機票。平台沒有自有商品，無官網業者也能上架。
大系統涵蓋旅客搜尋、業者商品管理與管理員審核，包含帳號、商品、梯次、報價和對話等資料。
創新用聊天或語音表達需求，帶出旅遊商品卡；需要靈感時提供目的地與影片建議。
吸引力旅客不用逐家整理搜尋條件；業者多一個展示商品、接觸旅客的入口。
技術可行規劃以網頁、資料庫及外部 AI API 實作；AI 整理需求，商品日期與價格由後端查詢。
多種類別可分析 User、Agency、TravelProduct、Departure、PriceQuote、Conversation 等類別。
資料分類／繼承TravelProduct 可分成 PackageTour、FlightHotelPackage、FlightTicket。例如日本五天團、機票加四晚住宿、單獨機票。
UML 工具使用 PlantUML 繪圖，可輸出 PNG、SVG；例：描述旅遊商品及三個子類別，產生繼承類別圖。
工具能力（老師建議）目前用於繪圖，尚未建立 UML 自動產生應用程式碼或程式碼反向產圖的流程。

老師題目我們的答案
1. Introduction：目的、動機協助旅客快速找到符合日期與預算的商品，並讓旅行社有共同的上架與媒合入口。
2. Current system：比較四個系統保留原四個系統，另加入易遊網與三個國外平台，共八個參考系統。老師原要求仍是三個類似系統加本系統。
3. Proposed system：提出的系統旅客以對話找商品，業者提交自己的商品，管理員審核後發布；平台負責展示與媒合。
3.1 Overview：系統概述輸入需求 → AI 整理條件 → 查商品 → 顯示旅遊卡 → 看詳情 → 聯絡業者。例：輸入「12月23日，日本五天，三萬元內」，查看符合條件的行程。
原四個系統＋四個新增參考
系統功能與優點限制／分析我們可參考的地方
雄獅旅遊呈現行程、出發日期與價格。起價不等於所選日期及人數的最終價格。分開顯示梯次日期與對應報價。
可樂旅遊可先選行程，也可先選日期。旅客仍需自行設定條件；操作負擔待測。保留日期與目的地兩種查找入口。
品冠旅遊字卡呈現特色、日期與起價。指定日期的實際費用須查商品。用短文字突出行程特色。
易遊網團體旅遊、機加酒、機票及日期篩選。商品類別與優惠多；找團步驟待測。標示供應業者，初期聚焦三種商品。
TourRadar整合多家業者的多天行程、價格與評價。國際機票一般不包含，須查各商品。清楚呈現天數、價格、業者與包含項目。
Travelstride比較行程與業者，展示 AI 客製規劃入口。AI 客製方案與現成商品須分開比較。區分靈感建議與真實業者商品。
TravelSupermarket比較套裝假期，轉往業者網站完成訂購。價格可能變動，稅費與附加項目需確認。清楚標來源與前往業者的入口。
本平台（規劃）對話搜尋、日期與價格優先、業者上架。依賴商品更新，AI 理解與成效待驗證。先做好日期、報價及商品來源。

我們的設計重點：以出發日期與價格找真實業者商品，支援無官網業者上架，並用簡單對話減少操作。Travelstride 已展示 AI 功能，因此不把「有 AI」說成獨有優勢。

官方資料查閱：2026/10/14。限制與參考方向含設計分析，未做操作優劣實測。TourRadar 機票說明；Travelstride 依官方搜尋索引查閱，未實測 AI。

本平台採用三項方向：TourRadar 的一致商品資訊、Travelstride 的旅遊建議，以及 TravelSupermarket 的業者轉接。介面採「聊天輸入 → 商品卡 → 完整詳情 → 聯絡業者」；商品卡先呈現日期、對應價格、天數與旅行社，其他日期、飯店、餐點與費用放詳情。靈感標為旅遊建議，不當作可購買商品；價格與包含項目依業者內文。

3.2 功能性需求（十項以上）18 項草案：AI／語音搜尋、修改條件、標籤、篩選排序、商品卡、詳情、比較、收藏追蹤、價格紀錄、降價出清提醒、註冊驗證、登入登出、忘記密碼、業者草稿、送審、審核發布、管理總覽、影片推薦。例：輸入日本五天需求 → 查看商品卡 → 收藏行程。
3.3 非功能性需求以下依 11 個分類整理簡答；完整 L10 P.52 尚未提供，未取得的原題仍待核對。
3.3.1 使用者類型旅客、旅行社人員、管理員。例如業者只管理自己的商品，管理員負責審核。
3.3.1 是否有多種類型的使用者？有，三種角色有不同入口與權限。
3.3.1 使用者需要哪些教學？旅客看搜尋範例，業者看上架與送審教學，管理員看審核教學。
3.3.1 容易學會是否重要？重要。旅客可直接說「日本五天，三萬元內」，系統整理條件後找商品。
3.3.1 是否防止使用者出錯？是。例如回程早於出發日，提示修正並保留其他欄位。
3.3.1 輸入／輸出設備鍵盤、滑鼠、觸控與麥克風輸入；螢幕、喇叭或耳機輸出。例：手機語音輸入需求，螢幕顯示商品卡。
3.3.2 Documentation：文件提供旅客使用說明、業者與管理員手冊、技術文件。例：業者依手冊填商品並送審，工程師依 UML 找到負責的類別。
3.3.2 文件讀者（問題摘要）使用說明給旅客，操作手冊給業者與管理員，技術文件給工程師及維運人員；此題完整原文待補。
3.3.3 Hardware considerations：硬體使用者以電腦、手機或平板上網；平台使用伺服器、資料庫與外部 AI。例：手機送出需求，後端查商品並回傳結果。
3.3.4 Performance characteristics：效能處理時顯示狀態，失敗保留輸入並可重試。例：AI 回應較慢時顯示處理中；速度與容量目標另待測。
3.3.5 Error handling：錯誤與極端情況區分輸入錯誤、查無結果與服務失敗。例：沒有符合商品時詢問是否調整，不能編造行程或零元價格。
3.3.6 System interfacing：串接以獨立介面串接 AI、語音及郵件。例：語音轉文字 → AI 整理 → 後端驗證 → 查商品。
3.3.7 Quality issues：品質日期、價格及可售資訊依業者來源。例：滑雪需求須有滑雪證據，不能只因商品在北海道就推薦。
3.3.8 System modifications：修改按功能分模組，修改時更新文件與測試。例：換 AI 供應商時透過 AI 介面替換，核對搜尋條件契約。
3.3.9 Physical environment：使用環境瀏覽器隨時可輸入需求，語音與文字可切換。例：吵雜場所改打字，斷線時盡量保留輸入。
3.3.10 Security issues：安全保護帳號、個資、權限及 AI 金鑰。例：A 旅行社不能修改 B 旅行社的商品。
3.3.11 Resources and management：資源管理業者維護商品，管理員審核，工程師維運。例：AI 達用量上限時停止新 AI 請求，一般搜尋仍可用。

11/21使用案例與類別分析⌄
老師題目我們的答案
3.5.2 Use case nameSearchTravelProducts（搜尋旅遊商品）。
Participating actors：職稱旅客、外部 AI 服務；使用職稱，不使用林柏諭等人名。
Entry condition：開始情況旅客開啟搜尋介面；系統可讀取業者已發布的商品資料。
Flow of events：主動句流程旅客輸入需求 → 系統整理並顯示條件 → 旅客補充或確認 → 系統驗證、查商品並顯示卡片 → 旅客查看詳情。
Exit condition：結束情況顯示符合條件的商品，或說明沒有符合結果。
Exceptions：例外日期不合理請修正；需求不清楚先追問；AI 失敗保留輸入並提供一般搜尋。
相關非功能性需求易學、防錯、來源正確、角色權限與 AI 用量上限。
3.5.3 文字分析：名詞 → 類別旅客 → User；旅行社 → Agency；商品 → TravelProduct；梯次 → Departure；報價 → PriceQuote；條件 → SearchCriteria。
文字分析：動詞 → 受詞的方法驗證搜尋條件 → SearchCriteria.validate()；判斷梯次日期是否符合 → Departure.matchesDate()。
文字分析：形容詞 → 屬性已發布 → publicationStatus；可售席次 → availableSeats；例如未知席次保留空值。
3.5.3.1 Data dictionary：資料字典例：productId（字串，T001）、departureId（字串，D001）、departureDate（日期，2026-12-23）、price（可空小數，29900.00）。
3.5.3.2 Class diagrams：類別圖以商品、梯次、報價、業者及搜尋條件為核心，依下列繼承、擁有與限定鍵關係製圖。
繼承關聯性TravelProduct → PackageTour、FlightHotelPackage、FlightTicket。例：日本五天團是一種 PackageTour。
擁有關聯性一個旅遊商品擁有多個梯次。例：T001 包含 12/23 的 D001 與另一日期的 D002。
Qualification：限定鍵在同一旅行社的商品集合，以業者商品編號取得唯一商品（0..1）。例：Agency A001 中的 JP005 對應 T001；編號須在該旅行社內唯一。
