11/7功能與非功能需求⌄

以下是作業版的未來需求設計，例子為設計資料；不代表AI、帳號或業者功能已完成。支援功能的開發優先順序另定。

3.2 功能性需求（18項）

功能詳細答案與例子
FR-01 AI／語音搜尋

做法：旅客不必先登入，可打字或使用麥克風輸入需求。語音先轉文字，外部 AI 整理日期、目的地、天數與預算，後端核對條件後查已發布商品；不清楚的條件先追問。

例子：輸入「我想去日本」→ 系統詢問出發日 → 回答「2026/12/23，五天，三萬元內」→ 確認條件 → 顯示符合的旅行社商品卡。AI 失敗時保留文字，提供重試或一般篩選。

FR-02 修改與還原條件

做法：旅客可接著修改一個條件，系統保留沒有修改的條件；成功搜尋後記錄上一輪條件，供旅客還原。

例子：原條件為12/23、日本、五天、三萬元內 → 輸入「改成四天」→ 只改天數並重新找商品 → 按還原回到五天；查詢失敗不清空原條件。

FR-03 快捷標籤

做法：點選目的地、天數或主題標籤，可把需求文字加入輸入框，再由旅客確認送出；不把大量標籤一次攤開。

例子：點「日本」和「溫泉」→ 輸入框加入對應文字 → 自己補上日期並搜尋。重複或矛盾條件需提示調整，不能讓畫面與實際查詢不同。

FR-04 篩選與排序

做法：先篩選指定日期、目的地、天數、出發地及預算，再依旅客選擇排列價格。沒有目的地可查不同地點；「便宜就好」代表低價優先，不代表系統自行設定預算上限。

例子：指定12/23、日本五天、三萬元內 → 顯示同日25,000元、28,000元的行程。若無符合商品，先詢問是否接受鄰近日期；不把其他日期混成符合結果。

FR-05 商品卡

做法：把商品、所選梯次及其報價組成旅遊卡，突出出發日、價格、天數與旅行社。套裝行程、機加酒、機票只顯示各自適用欄位。

例子：卡片顯示「12/23出發、日本五天、每人28,000元、某旅行社」→ 點卡片開同一商品詳情。價格未知標「待確認」，測試資料清楚標示為範例。

FR-06 商品詳情與來源

做法：提供獨立頁面，呈現每日行程、不同日期報價、航班、飯店、餐點、費用及業者窗口；有官網可連到原商品，無官網業者使用經審核的平台商品頁。

例子：旅客看完北海道五天內容 → 換12/24，價格與回程一起更新 → 決定購買時前往業者商品頁或聯絡窗口。未提供的餐點、稅費標待確認；平台不自行承諾名額。

FR-07 少量商品比較

做法：旅客可自行加入2～3個商品，對照日期、對應價格、天數及出發地；比較是輔助功能，不要求旅客先比較才能聯絡業者。

例子：加入同日出發的兩個五天團 → 對照28,000元與30,000元及行程差異 → 選其中一個看詳情；加入第四筆時提示先移除一筆。

FR-08 收藏與追蹤清單

做法：保存旅客選擇的商品及梯次，支援取消收藏。訪客清單限同一裝置；登入後可選擇合併並去除重複，會員清單只對本人開放。

例子：先收藏12/23的日本五天行程 → 登入後合併到自己的清單 → 下次再看。收藏不代表訂位、保留價格或已開啟通知。

FR-09 價格紀錄

做法：取得可信的新報價後，記下同商品、同梯次、相同費用條件的價格及觀測時間；讀取畫面本身不新增價格紀錄。

例子：同一梯次先記錄40,000元，之後記錄36,000元 → 清單顯示兩筆日期與價格；不同出發日、幣別或方案不能直接算成降價。沒有紀錄時明確顯示。

FR-10 降價／出清提醒

做法：旅客可設定降價門檻、出清提醒及關閉通知。有效新報價達門檻才建立網站通知；LINE需完成對應串接與綁定後使用。出清必須有業者標示，不能只因便宜就稱出清。

例子：基準價40,000元、門檻10% → 同梯次降到36,000元且仍有效 → 建立一筆通知；再次檢查同一事件不重複發送。過期、未知價格不觸發降價提醒。

FR-11 Email註冊與驗證

做法：以Email作為帳號，旅客填密碼與顯示名稱後建立待驗證帳號；有效驗證連結只能使用一次，過期可申請重寄。一般註冊不會取得業者或管理員權限。

例子：填資料 → 系統檢查Email與密碼 → 寄出驗證信 → 點有效連結啟用 → 可以登入；寄信失敗需提示，不宣稱已成功寄達。

FR-12 登入、登出與角色入口

做法：登入後依角色提供旅客、旅行社及管理員功能；每次受保護操作都由後端驗證身分與權限。登出後仍可瀏覽公開商品。

例子：旅客登入只見自己的收藏；業者登入可管理自己的商品；管理員可審核。旅客直接輸入後台網址，也不能讀寫業者草稿。

FR-13 忘記密碼

做法：使用Email申請限時、一次性的重設連結；新密碼通過規則後更新，撤銷舊登入狀態。畫面不公開某個Email是否已註冊。

例子：提交Email → 收到重設信 → 設新密碼 → 使用新密碼登入；舊連結第二次使用或過期時拒絕，提供重新申請入口。

FR-14 業者商品草稿

做法：旅行社人員建立或修改自己的商品、梯次、價格、內容及窗口，儲存草稿與版本。外部商品網址可選填，讓無官網旅行社也能準備上架。

例子：無官網業者填日本五天商品及LINE窗口 → 儲存草稿 → 修改價格再存一個版本。旅客搜尋不到未發布草稿，業者也不能修改其他公司的草稿。

FR-15 商品送審

做法：業者完成資料後送審，系統檢查必要欄位並記錄狀態、版本與時間；業者可看退回原因，修正後再送。

例子：業者送審 → 狀態變待審核 → 管理員退回「請補費用說明」→ 業者補資料並再送。已待審的同一份資料不重複建立送審紀錄。

FR-16 審核與發布

做法：管理員核對來源、商品內容、日期、報價與業者窗口，選擇核准發布或附原因退回；發布時商品、梯次及報價要一起完成。

例子：管理員核准資料完整的商品 → 平台建立公開商品頁 → 旅客搜尋得到；費用不清楚的商品退回後仍不公開。寫入失敗不能留下半套已發布資料。

FR-17 管理總覽

做法：管理員查看待審商品、處理狀態與必要統計，再進入對應項目處理；查看總覽不會自動核准或改價。

例子：總覽有兩份待審 → 打開第一份並退回 → 回總覽時該份顯示需修改。查詢失敗顯示重試提示，不能把錯誤當成零筆待審。

FR-18 旅遊靈感與影片

做法：旅客目的地未定時，AI提供少量旅遊建議及理由；旅客確認後才改搜尋條件。規劃每5張商品卡搭配1張相關影片卡，影片與可購買商品分開，來源及授權方式仍待確認。

例子：旅客說「12月想玩雪，地點不限」→ 看建議後選日本 → 系統查日本商品。影片只補充介紹，不能當作價格或可售證據；沒有可信來源時不編造影片或商品。

物件導向（OO）對照

上述需求適合用物件導向設計。需求表說明系統要做什麼，再透過類別、資料與方法分配責任；目前已有前端示例，完整平台仍待逐步完成。

需求對應物件與方法
旅行社管理商品Agency：透過 addProduct() 加入商品、findProduct() 查找自己的商品集合。
商品有不同出發日期TravelProduct、Departure：透過 quoteAt(index) 取得指定梯次。
每個日期有對應價格PriceQuote：保存金額與費用說明，透過 label 等 getter 提供讀取。
  • 封裝：PriceQuote 用私有欄位 #amount 保存金額，建立時檢查價格，外部透過 getter 讀取。
  • 繼承：PackageTour（套裝行程）、FlightHotelPackage（機加酒）、FlightTicket（機票）繼承 TravelProduct（旅遊商品）。
  • 多型：商品卡統一呼叫 getSummary()，不同商品子類別回傳自己的摘要。
  • 擁有關係：旅行社有商品，商品有出發梯次，每個梯次有對應報價。

上台說法：「我們把旅行社、商品、梯次與報價設計成不同物件，讓每個物件管理自己的資料，並透過方法合作完成需求。」

這些例子對應目前的前端示範；商品集合查找不等於後端權限驗證，也不表示完整AI系統已完成。

3.3 非功能性需求

以下說明系統在操作、品質與維護方面的規劃。

需求分類我們的做法
3.3.1 哪些使用者會使用？主要有旅客、旅行社人員和管理員，分別負責找行程、上架商品和審核商品。旅客可以先搜尋，不必一進網站就登入。
3.3.1 是否有多種類型的使用者？有。不同角色看到不同功能：旅客看收藏，旅行社看自己的商品，管理員看審核清單；系統也會檢查權限，不能只靠隱藏按鈕。
3.3.1 使用者需要哪些教學？旅客提供搜尋例句；旅行社提供填商品、送審和修改的說明；管理員提供審核步驟。例如業者照填寫範例完成商品後，就能送出審核。
3.3.1 容易學會是否重要？重要。旅客輸入「12/23，日本五天，三萬元內」就能開始找行程，不用先學會一整套篩選操作。缺少日期等重要條件時，系統再詢問。
3.3.1 是否應防止操作錯誤？會。資料不合理時，指出需要修改的地方，並保留其他已填內容。例如回程早於出發日，系統會請使用者修正日期。
3.3.1 有哪些輸入／輸出設備？可用鍵盤、滑鼠、手機觸控或麥克風輸入，結果顯示在螢幕上；影片聲音由喇叭或耳機播放。不方便說話或不能使用麥克風時，仍可打字搜尋。
3.3.2 需要哪些文件？提供旅客操作說明、旅行社上架說明、管理員審核說明，以及開發人員使用的程式與UML文件。內容應跟目前版本一致。
3.3.2 文件讀者旅客看如何找行程，旅行社看如何上架，管理員看如何審核；開發與維運人員看程式架構及問題處理方式，讓每個人容易找到自己需要的內容。
3.3.3 硬體考量使用者可用能上網的電腦、手機或平板。AI運算和商品查詢由伺服器處理，使用者不需要準備高階電腦。
3.3.4 效能特性搜尋應快速回應，等待AI時顯示處理中。若超過設定時間仍沒有結果，就保留原需求，提示使用者重試或改用一般篩選；實際速度仍需測試。
3.3.5 錯誤與極端情況系統要說清楚是輸入有誤、沒有符合行程，還是服務暫時失敗。例如找不到12/23的日本團，就詢問是否改日期，不能編出行程或價格。
3.3.6 系統串接語音先轉成文字，AI再整理旅遊條件，後端確認後查旅行社商品；註冊與忘記密碼會使用郵件服務。任何服務失敗都要顯示提示。
3.3.7 品質問題日期、價格與費用以旅行社提供的資料為準，缺資料就標待確認。例如搜尋滑雪時，行程要真的包含滑雪活動；切換出發日也要顯示該日價格。
3.3.8 系統修改不同功能分開管理，修改時保留版本並更新相關說明。例如更換AI服務後，仍要確認日期和預算能正確傳給商品搜尋；出問題時可回復原版本。
3.3.9 實際使用環境要能在電腦和手機上清楚操作。吵雜場所可改用文字；傳送途中斷線時，保留本頁已輸入的需求，讓使用者恢復網路後重試。
3.3.10 安全問題旅客只能看自己的私人資料，旅行社只能修改自己的商品。例如A旅行社不能改B旅行社的價格。密碼不存明文，AI金鑰留在後端，重設密碼連結需限時且只能使用一次。
3.3.11 資源與管理旅行社更新商品，管理員審核，工程師維護系統並備份資料。AI用量設上限；到上限後暫停新的AI請求，但仍可用一般搜尋找行程。

3.5.2 Use case nameSearchTravelProducts（搜尋旅遊商品）。
Participating actors：職稱旅客、外部 AI 服務；使用職稱，不使用林柏諭等人名。
Entry condition：開始情況旅客開啟搜尋介面；系統可讀取業者已發布的商品資料。
Flow of events：主動句流程旅客輸入需求 → 系統整理並顯示條件 → 旅客補充或確認 → 系統驗證、查商品並顯示卡片 → 旅客查看詳情。
Exit condition：結束情況顯示符合條件的商品，或說明沒有符合結果。
Exceptions：例外日期不合理請修正；需求不清楚先追問；AI 失敗保留輸入並提供一般搜尋。
相關非功能性需求易學、防錯、來源正確、角色權限與 AI 用量上限。
3.5.3 文字分析：名詞 → 類別旅客 → User；旅行社 → Agency；商品 → TravelProduct；梯次 → Departure；報價 → PriceQuote；條件 → SearchCriteria。
文字分析：動詞 → 受詞的方法驗證搜尋條件 → SearchCriteria.validate()；判斷梯次日期是否符合 → Departure.matchesDate()。
文字分析：形容詞 → 屬性已發布 → publicationStatus；可售席次 → availableSeats；例如未知席次保留空值。
3.5.3.1 Data dictionary：資料字典例：productId（字串，T001）、departureId（字串，D001）、departureDate（日期，2026-12-23）、price（可空小數，29900.00）。
