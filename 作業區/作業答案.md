| 本平台（規劃） | 對話搜尋、日期與價格優先、業者上架。 | 依賴商品更新，AI 理解與成效待驗證。 | 先做好日期、報價及商品來源。 |

我們的設計重點：以出發日期與價格找真實業者商品，支援無官網業者上架，並用簡單對話減少操作。Travelstride 已展示 AI 功能，因此不把「有 AI」說成獨有優勢。

本平台採用三項方向：TourRadar 的一致商品資訊、Travelstride 的旅遊建議，以及 TravelSupermarket 的業者轉接。介面採「聊天輸入 → 商品卡 → 完整詳情 → 聯絡業者」；商品卡先呈現日期、對應價格、天數與旅行社，其他日期、飯店、餐點與費用放詳情。靈感標為旅遊建議，不當作可購買商品；價格與包含項目依業者內文。

[獨立畫面提案](獨立展示/index.html)：下載後開啟；組員可編輯，正式整合位置待確認。

網站功能依官方資料查閱（2026/10/14）；限制與參考方向含設計分析，尚未實測操作優劣。TourRadar 機票說明：[官方 FAQ](https://www.tourradar.com/contact)。Travelstride 依官方搜尋索引查閱，未實測 AI。

## 11/21 使用案例與類別分析

| 老師題目 | 我們的答案 |
| --- | --- |
| 3.5.2 Use case name | SearchTravelProducts（搜尋旅遊商品）。 |
| Participating actors：職稱 | 旅客、外部 AI 服務；使用職稱，不使用林柏諭等人名。 |
| Entry condition：開始情況 | 旅客開啟搜尋介面；系統可讀取業者已發布的商品資料。 |
| Flow of events：主動句流程 | 旅客輸入需求 → 系統整理並顯示條件 → 旅客補充或確認 → 系統驗證、查商品並顯示卡片 → 旅客查看詳情。 |
| Exit condition：結束情況 | 顯示符合條件的商品，或說明沒有符合結果。 |
| Exceptions：例外 | 日期不合理請修正；需求不清楚先追問；AI 失敗保留輸入並提供一般搜尋。 |
| 相關非功能性需求 | 易學、防錯、來源正確、角色權限與 AI 用量上限。 |
| 3.5.3 文字分析：名詞 → 類別 | 旅客 → User；旅行社 → Agency；商品 → TravelProduct；梯次 → Departure；報價 → PriceQuote；條件 → SearchCriteria。 |
| 文字分析：動詞 → 受詞的方法 | 驗證搜尋條件 → SearchCriteria.validate()；判斷梯次日期是否符合 → Departure.matchesDate()。 |
| 文字分析：形容詞 → 屬性 | 已發布 → publicationStatus；可售席次 → availableSeats；例如未知席次保留空值。 |
| 3.5.3.1 Data dictionary：資料字典 | 例：productId（字串，T001）、departureId（字串，D001）、departureDate（日期，2026-12-23）、price（可空小數，29900.00）。 |
| 3.5.3.2 Class diagrams：類別圖 | 以商品、梯次、報價、業者及搜尋條件為核心，依下列繼承、擁有與限定鍵關係製圖。 |
| 繼承關聯性 | TravelProduct → PackageTour、FlightHotelPackage、FlightTicket。例：日本五天團是一種 PackageTour。 |
| 擁有關聯性 | 一個旅遊商品擁有多個梯次。例：T001 包含 12/23 的 D001 與另一日期的 D002。 |
| Qualification：限定鍵 | 在同一旅行社的商品集合，以業者商品編號取得唯一商品（0..1）。例：Agency A001 中的 JP005 對應 T001；編號須在該旅行社內唯一。 |
