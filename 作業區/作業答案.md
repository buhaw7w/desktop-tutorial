我們的設計重點：以出發日期與價格找真實業者商品，支援無官網業者上架，並用簡單對話減少操作。Travelstride 已展示 AI 功能，因此不把「有 AI」說成獨有優勢。

本平台採用三項方向：TourRadar 的一致商品資訊、Travelstride 的旅遊建議，以及 TravelSupermarket 的業者轉接。介面採「聊天輸入 → 商品卡 → 完整詳情 → 聯絡業者」；商品卡先呈現日期、對應價格、天數與旅行社，其他日期、飯店、餐點與費用放詳情。靈感標為旅遊建議，不當作可購買商品；價格與包含項目依業者內文。

[獨立畫面提案](獨立展示/index.html)：下載後開啟；組員可編輯，正式整合位置待確認。

網站功能依官方資料查閱（2026/10/14）；限制與參考方向含設計分析，尚未實測操作優劣。TourRadar 機票說明：[官方 FAQ](https://www.tourradar.com/contact)。Travelstride 依官方搜尋索引查閱，未實測 AI。

## 11/7 功能與非功能需求

以下是作業版的未來需求設計，例子為設計資料；不代表AI、帳號或業者功能已完成。支援功能的開發優先順序另定。

### 3.2 功能性需求（18項）

| 功能 | 詳細答案與例子 |
| --- | --- |
| FR-01 AI／語音搜尋 | **做法：**旅客不必先登入，可打字或使用麥克風輸入需求。語音先轉文字，外部 AI 整理日期、目的地、天數與預算，後端核對條件後查已發布商品；不清楚的條件先追問。<br>**例子：**輸入「我想去日本」→ 系統詢問出發日 → 回答「2026/12/23，五天，三萬元內」→ 確認條件 → 顯示符合的旅行社商品卡。AI 失敗時保留文字，提供重試或一般篩選。 |
| FR-02 修改與還原條件 | **做法：**旅客可接著修改一個條件，系統保留沒有修改的條件；成功搜尋後記錄上一輪條件，供旅客還原。<br>**例子：**原條件為12/23、日本、五天、三萬元內 → 輸入「改成四天」→ 只改天數並重新找商品 → 按還原回到五天；查詢失敗不清空原條件。 |
| FR-03 快捷標籤 | **做法：**點選目的地、天數或主題標籤，可把需求文字加入輸入框，再由旅客確認送出；不把大量標籤一次攤開。<br>**例子：**點「日本」和「溫泉」→ 輸入框加入對應文字 → 自己補上日期並搜尋。重複或矛盾條件需提示調整，不能讓畫面與實際查詢不同。 |
| FR-04 篩選與排序 | **做法：**先篩選指定日期、目的地、天數、出發地及預算，再依旅客選擇排列價格。沒有目的地可查不同地點；「便宜就好」代表低價優先，不代表系統自行設定預算上限。<br>**例子：**指定12/23、日本五天、三萬元內 → 顯示同日25,000元、28,000元的行程。若無符合商品，先詢問是否接受鄰近日期；不把其他日期混成符合結果。 |
| FR-05 商品卡 | **做法：**把商品、所選梯次及其報價組成旅遊卡，突出出發日、價格、天數與旅行社。套裝行程、機加酒、機票只顯示各自適用欄位。<br>**例子：**卡片顯示「12/23出發、日本五天、每人28,000元、某旅行社」→ 點卡片開同一商品詳情。價格未知標「待確認」，測試資料清楚標示為範例。 |
| FR-06 商品詳情與來源 | **做法：**提供獨立頁面，呈現每日行程、不同日期報價、航班、飯店、餐點、費用及業者窗口；有官網可連到原商品，無官網業者使用經審核的平台商品頁。<br>**例子：**旅客看完北海道五天內容 → 換12/24，價格與回程一起更新 → 決定購買時前往業者商品頁或聯絡窗口。未提供的餐點、稅費標待確認；平台不自行承諾名額。 |
| FR-07 少量商品比較 | **做法：**旅客可自行加入2～3個商品，對照日期、對應價格、天數及出發地；比較是輔助功能，不要求旅客先比較才能聯絡業者。<br>**例子：**加入同日出發的兩個五天團 → 對照28,000元與30,000元及行程差異 → 選其中一個看詳情；加入第四筆時提示先移除一筆。 |
| FR-08 收藏與追蹤清單 | **做法：**保存旅客選擇的商品及梯次，支援取消收藏。訪客清單限同一裝置；登入後可選擇合併並去除重複，會員清單只對本人開放。<br>**例子：**先收藏12/23的日本五天行程 → 登入後合併到自己的清單 → 下次再看。收藏不代表訂位、保留價格或已開啟通知。 |
| FR-09 價格紀錄 | **做法：**取得可信的新報價後，記下同商品、同梯次、相同費用條件的價格及觀測時間；讀取畫面本身不新增價格紀錄。<br>**例子：**同一梯次先記錄40,000元，之後記錄36,000元 → 清單顯示兩筆日期與價格；不同出發日、幣別或方案不能直接算成降價。沒有紀錄時明確顯示。 |
| FR-10 降價／出清提醒 | **做法：**旅客可設定降價門檻、出清提醒及關閉通知。有效新報價達門檻才建立網站通知；LINE需完成對應串接與綁定後使用。出清必須有業者標示，不能只因便宜就稱出清。<br>**例子：**基準價40,000元、門檻10% → 同梯次降到36,000元且仍有效 → 建立一筆通知；再次檢查同一事件不重複發送。過期、未知價格不觸發降價提醒。 |
| FR-11 Email註冊與驗證 | **做法：**以Email作為帳號，旅客填密碼與顯示名稱後建立待驗證帳號；有效驗證連結只能使用一次，過期可申請重寄。一般註冊不會取得業者或管理員權限。<br>**例子：**填資料 → 系統檢查Email與密碼 → 寄出驗證信 → 點有效連結啟用 → 可以登入；寄信失敗需提示，不宣稱已成功寄達。 |
| FR-12 登入、登出與角色入口 | **做法：**登入後依角色提供旅客、旅行社及管理員功能；每次受保護操作都由後端驗證身分與權限。登出後仍可瀏覽公開商品。<br>**例子：**旅客登入只見自己的收藏；業者登入可管理自己的商品；管理員可審核。旅客直接輸入後台網址，也不能讀寫業者草稿。 |
| FR-13 忘記密碼 | **做法：**使用Email申請限時、一次性的重設連結；新密碼通過規則後更新，撤銷舊登入狀態。畫面不公開某個Email是否已註冊。<br>**例子：**提交Email → 收到重設信 → 設新密碼 → 使用新密碼登入；舊連結第二次使用或過期時拒絕，提供重新申請入口。 |
| FR-14 業者商品草稿 | **做法：**旅行社人員建立或修改自己的商品、梯次、價格、內容及窗口，儲存草稿與版本。外部商品網址可選填，讓無官網旅行社也能準備上架。<br>**例子：**無官網業者填日本五天商品及LINE窗口 → 儲存草稿 → 修改價格再存一個版本。旅客搜尋不到未發布草稿，業者也不能修改其他公司的草稿。 |
| FR-15 商品送審 | **做法：**業者完成資料後送審，系統檢查必要欄位並記錄狀態、版本與時間；業者可看退回原因，修正後再送。<br>**例子：**業者送審 → 狀態變待審核 → 管理員退回「請補費用說明」→ 業者補資料並再送。已待審的同一份資料不重複建立送審紀錄。 |
| FR-16 審核與發布 | **做法：**管理員核對來源、商品內容、日期、報價與業者窗口，選擇核准發布或附原因退回；發布時商品、梯次及報價要一起完成。<br>**例子：**管理員核准資料完整的商品 → 平台建立公開商品頁 → 旅客搜尋得到；費用不清楚的商品退回後仍不公開。寫入失敗不能留下半套已發布資料。 |
| FR-17 管理總覽 | **做法：**管理員查看待審商品、處理狀態與必要統計，再進入對應項目處理；查看總覽不會自動核准或改價。<br>**例子：**總覽有兩份待審 → 打開第一份並退回 → 回總覽時該份顯示需修改。查詢失敗顯示重試提示，不能把錯誤當成零筆待審。 |
| FR-18 旅遊靈感與影片 | **做法：**旅客目的地未定時，AI提供少量旅遊建議及理由；旅客確認後才改搜尋條件。規劃每5張商品卡搭配1張相關影片卡，影片與可購買商品分開，來源及授權方式仍待確認。<br>**例子：**旅客說「12月想玩雪，地點不限」→ 看建議後選日本 → 系統查日本商品。影片只補充介紹，不能當作價格或可售證據；沒有可信來源時不編造影片或商品。 |

### 3.3 非功能性需求

3.3.1六題與文件需求依已提供照片整理；其餘是依老師11個分類補充的設計答案。完整L10 P.52仍待提供核對，不把補充設計當成老師原題。效能數值為暫訂驗收目標，尚未實測。

| 老師題目／需求分類 | 詳細答案、例子與檢查方式 |
| --- | --- |
| 3.3.1 哪些使用者會使用？ | **答案：**包含旅客、旅行社人員及管理員。旅客搜尋、看詳情和收藏；旅行社管理自己的商品；管理員審核與發布。公開搜尋不要求先登入。<br>**例子：**無官網旅行社準備商品，管理員核准後，未登入旅客也能搜尋並查看詳情。<br>**檢查：**核對三種角色的入口與操作權限，旅客不得取得上架、改價或審核權限。 |
| 3.3.1 是否有多種類型的使用者？ | **答案：**有。同一平台依登入角色顯示適合的功能，同時由後端檢查每次請求；不能只靠把按鈕藏起來限制操作。<br>**例子：**A旅行社人員與B旅行社人員使用相同上架介面，但各自只能讀寫自己的草稿。<br>**檢查：**用三種角色測試同一受保護網址；未授權者應被拒絕且不取得草稿資料。 |
| 3.3.1 使用者需要哪些教學？ | **答案：**旅客提供搜尋例句和短提示；旅行社提供填寫、儲存、送審及退回修正說明；管理員提供審核檢查項目。教學以當下操作為主。<br>**例子：**業者看一份完整填寫範例，填日期、價格與費用說明後送審；被退回時可依原因找到要改的欄位。<br>**檢查：**請第一次使用的人照提示完成指定任務，記錄需要求助的步驟，再修正提示。 |
| 3.3.1 容易學會是否重要？ | **答案：**重要。保留直接說需求的主入口，先顯示日期、價格與天數，其他資訊進詳情再看；缺條件才追問，不反覆要求已提供的資料。<br>**例子：**輸入「12/23、日本五天、便宜就好」→ 系統整理條件並依低價排列，不要求先選完一整頁標籤。<br>**檢查：**觀察首次使用者能否完成輸入、看結果、開詳情三步，並記錄完成時間、誤點及離開位置。 |
| 3.3.1 是否應防止操作錯誤？ | **答案：**需要。前後端都檢查日期先後、金額、必要欄位與權限；錯誤訊息指出哪裡要改，並保留其他合法輸入。發布前顯示待確認內容。<br>**例子：**業者填12/27出發、12/23返回 → 系統指出回程不能早於出發，保留商品名與其他欄位，不送出草稿。<br>**檢查：**提交錯日期、負數價格及缺必填資料，確認均被拒絕；修正後可以重新送出。 |
| 3.3.1 有哪些輸入／輸出設備？ | **答案：**支援鍵盤、滑鼠、觸控與可用的麥克風輸入，透過螢幕顯示文字與商品卡；影片如含聲音，可由喇叭或耳機輸出。語音無法使用時仍可打字。<br>**例子：**手機使用者允許麥克風後說出需求，確認辨識文字再送出；不開麥克風時改用文字框。<br>**檢查：**測試電腦與手機操作、鍵盤選取和麥克風拒絕授權的情況，不讓單一設備失效阻斷搜尋。 |
| 3.3.2 需要哪些文件？ | **答案：**規劃旅客使用說明、業者上架／送審說明、管理員審核說明，以及工程師使用的UML、類別方法與維運紀錄。文件要與目前版本一致。<br>**例子：**修改日期切換功能時，同時修正相關程式說明與循序圖，讓上台報告能對照相同方法名稱。<br>**檢查：**抽查一個功能的操作、圖表與程式名稱是否相符；尚未實作的部分明確標示為規劃。 |
| 3.3.2 文件讀者（問題摘要） | **答案：**旅客閱讀操作範例，旅行社與管理員閱讀各自的流程，開發及維運人員閱讀類別、介面、部署與錯誤處理說明。此題完整講義原文仍待補。<br>**例子：**旅客只需要知道如何搜尋與看詳情；維運人員則需要知道AI逾時時如何查紀錄及恢復服務。<br>**檢查：**依角色抽查文件是否能完成其任務，避免把所有技術說明塞進一般使用入口。 |
| 3.3.3 硬體考量（補充設計） | **答案：**使用者以可上網的電腦、手機或平板操作；平台規劃應用伺服器、資料庫及外部AI服務，不要求使用者自行訓練模型或準備高階顯示卡。<br>**例子：**一般手機送出文字需求 → 伺服器整理條件、查資料 → 回傳可閱讀的商品卡；不支援語音的裝置仍能搜尋。<br>**檢查：**在選定的桌面與手機瀏覽器測試顯示及操作；伺服器規格依壓力測試調整，尚未定案。 |
| 3.3.4 效能特性（補充設計） | **答案：**搜尋與AI處理期間顯示狀態，避免重複送出；資料分批載入。暫訂驗收目標：1,000筆測試商品、10人同時一般搜尋時，95%請求於3秒內完成；AI請求超過20秒顯示逾時及替代入口。這些是待驗證目標。<br>**例子：**AI遲遲未回覆 → 畫面保留原需求並顯示逾時 → 旅客選擇重試或一般篩選；系統不把尚未完成的請求說成查無商品。<br>**檢查：**記錄測試環境、資料量、同時人數、95百分位時間與失敗率；不把單次測試當成正式容量保證。 |
| 3.3.5 錯誤與極端情況（補充設計） | **答案：**區分輸入不合法、沒有符合商品、商品失效與外部服務失敗，分別提示可採取的動作；不以假價格、假行程或空白畫面代替錯誤。<br>**例子：**條件正確但找不到12/23日本五天商品 → 顯示沒有符合結果並詢問是否改日期；若資料庫失敗，則顯示暫時無法查詢。<br>**檢查：**分別測試錯日期、零筆結果、失效商品、斷線與AI逾時，確認訊息不同且保留可重試的輸入。 |
| 3.3.6 系統串接（補充設計） | **答案：**語音、AI與郵件透過獨立介面串接。AI輸出的條件須經後端檢查，價格與名額只讀業者商品資料；每個外部服務都處理失敗與逾時。<br>**例子：**語音轉文字 → AI回傳日本、12/23、五天 → 後端驗證日期和欄位 → 查已發布商品；AI回傳不存在的商品編號時，不直接展示。<br>**檢查：**測試正確、缺欄位、格式錯誤與逾時回應；郵件服務失敗時不顯示已成功寄達。 |
| 3.3.7 品質問題（補充設計） | **答案：**商品日期、價格、費用、業者及更新時間必須可追溯，卡片與詳情使用同一梯次；未知資訊標待確認。旅遊主題需有實際行程證據，推薦建議與真實商品分開。<br>**例子：**滑雪需求只能匹配有滑雪場、課程等相關內容的商品；不能僅因目的地是北海道就說有滑雪。換出發日也要換對應報價。<br>**檢查：**以有／無主題證據、不同日期價格及缺資料商品交叉測試，核對來源，確認不編造費用或席次。 |
| 3.3.8 系統修改（補充設計） | **答案：**按畫面、控制、資料模型及外部服務分責任，透過Git保留變更；修改前備份，修改後檢查相關功能與文件，提供可回復的版本。<br>**例子：**更換AI服務時沿用搜尋條件格式，確認日期、預算、商品查詢結果仍相同，並更新串接說明。<br>**檢查：**比較修改前後的代表性例子；新版本失敗時可回到已知正常版本，不能直接覆蓋且沒有紀錄。 |
| 3.3.9 實際使用環境（補充設計） | **答案：**考量家中、通勤、公共場所及網路不穩等情況；文字與語音可切換，小螢幕保留清楚可點的按鈕，錯誤後盡量保留本頁輸入。<br>**例子：**吵雜車站改用打字；傳送途中斷線時保留畫面中的需求，恢復網路後由旅客重試。<br>**檢查：**測試窄螢幕、放大文字、拒絕麥克風及傳送途中斷線；不承諾清除瀏覽器資料或關閉私人模式後仍可還原。 |
| 3.3.10 安全問題（補充設計） | **答案：**保護帳號、私人對話、收藏及商品權限。密碼不存明文，驗證與重設連結需到期且限一次；正式連線使用HTTPS，AI金鑰留後端，紀錄避免保存密碼與金鑰。<br>**例子：**A旅行社即使改網址中的商品編號，也不能讀寫B旅行社草稿；旅客只能查看自己的收藏。失效重設連結不可再次改密碼。<br>**檢查：**測試跨業者、跨會員、未登入請求及過期連結；檢查前端與共用儲存庫沒有服務金鑰。媒合平台仍須防止帳號與商品遭冒用。 |
| 3.3.11 資源與管理（補充設計） | **答案：**業者維護來源商品，管理員審核，工程師處理維運與異常；組內具名分工另訂。記錄外部AI用量並設定額度與提醒，避免無限制重試；重要資料備份後需驗證能還原。<br>**例子：**AI達到設定額度 → 停止新AI請求並提示 → 一般搜尋仍可使用；商品更新失敗由負責人處理，不能悄悄把舊價當即時價。<br>**檢查：**模擬額度用盡、服務失敗及資料還原，確認替代入口可用、有人負責追蹤，並留下處理紀錄。 |
